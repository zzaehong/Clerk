첨부된 제품 기획서를 먼저 끝까지 읽고, 이 프로젝트의 목적과 MVP 범위를 충분히 이해한 뒤 작업을 시작해줘.

제품 기획서를 이 프로젝트의 **Source of Truth**로 사용한다.

이 프로젝트의 핵심 원칙은 다음과 같다.

> **Codex에서 터미널만 제거한다.**

우리는 새로운 AI 에이전트, 문서 편집기, IDE, 웹서비스를 만드는 것이 아니다.

이 프로그램은 **사용자의 컴퓨터에서 로컬로 실행되는 Codex CLI에 GUI를 덧붙이는 데스크톱 프로그램**이다.

Codex가 이미 가지고 있는 파일 탐색, 명령 실행, 파일 생성·수정, 추론, 작업 관리 등의 능력을 최대한 그대로 활용하면서 비개발자가 터미널을 사용하지 않고 Codex를 사용할 수 있게 만드는 것이 목표다.

---

# 1. 가장 중요한 개발 원칙

다음 원칙을 반드시 지켜줘.

* Codex가 이미 제공하는 기능은 재구현하지 않는다.
* 자체 AI Agent를 만들지 않는다.
* 자체 RAG / Vector DB / Embedding 시스템을 만들지 않는다.
* 자체 문서 편집기를 만들지 않는다.
* 자체 Git / Diff / Undo 시스템을 만들지 않는다.
* 자체 AI Router나 Prompt Optimizer를 만들지 않는다.
* 별도의 웹 Backend를 만들지 않는다.
* 별도의 Cloud Server를 만들지 않는다.
* Serverless 서비스로 구현하지 않는다.
* 사용자 파일이나 채팅을 외부 서버에 별도로 저장하지 않는다.
* 새로운 Dependency는 명확한 필요성이 있을 때만 추가한다.
* 추후 필요할 것 같다는 이유만으로 추상화하거나 기능을 만들지 않는다.
* MVP에 필요하지 않은 기능은 구현하지 않는다.

이 프로젝트는 반드시 다음 구조를 기본 전제로 한다.

```text
사용자의 PC

┌───────────────────────────────┐
│      Local Desktop App        │
│                               │
│        GUI                    │
│         │                     │
│         ▼                     │
│   Codex CLI / app-server      │
│         │                     │
│         ▼                     │
│   Local Filesystem            │
└───────────────────────────────┘
```

즉,

```text
웹사이트
→ 원격 서버
→ AI
```

구조가 아니다.

기본 구조는:

```text
로컬 GUI
→ 로컬 Codex
→ 로컬 파일
```

이다.

가능한 한 Codex 자체 기능을 그대로 사용하고, 우리 프로그램은 **Codex와 사용자를 연결하는 Presentation Layer** 역할에 집중한다.

---

# 2. 제품에서 사용하는 용어

사용자에게 개발자용 기술 용어를 그대로 노출하지 않는다.

특히 `Thread`라는 표현은 사용자 인터페이스와 제품 문서에서 사용하지 않는다.

대신 다음 표현을 사용한다.

```text
Thread
→ 채팅
또는
→ 작업
```

상황에 따라 다음과 같이 구분한다.

### 채팅

사용자가 Codex와 주고받는 하나의 대화.

예:

* 새 채팅
* 이전 채팅 이어하기
* 최근 채팅

### 작업

Codex가 사용자의 요청을 처리하는 하나의 실행 과정.

예:

* 작업 중
* 작업 완료
* 작업 중지

Codex 공식 프로토콜의 실제 API 이름이 `thread/start`, `thread/resume` 등인 경우 내부 코드와 기술 구현에서는 공식 명칭을 그대로 사용할 수 있다.

그러나 사용자 UI에서는 이를 `채팅 시작`, `채팅 이어하기` 등으로 표현한다.

# 3. 이번 작업의 목표

이번 단계에서는 완성된 제품을 만들지 않는다.

먼저 **최소 기술 PoC(Proof of Concept)** 를 만들어 다음 흐름이 실제로 동작하는지 검증한다.

```text
로컬 프로그램 실행
↓
로컬 폴더 선택
↓
로컬 Codex 실행 및 연결
↓
선택한 폴더를 작업 위치로 설정
↓
새 채팅 시작
↓
사용자 자연어 입력
↓
Codex 작업 실행
↓
Streaming / Event 수신
↓
필요한 Approval 또는 사용자 질문 처리
↓
로컬 파일 생성 / 수정
↓
작업 완료
↓
Codex 사용량 표시
↓
프로그램 재실행
↓
기존 채팅 이어하기
```

이 전체 사이클이 실제 로컬 환경에서 작동하는 것이 이번 단계의 성공 기준이다.

---

# 4. 기술 방향

우선 다음 구조를 기준으로 검토해줘.

* Application Type: Local Desktop Application
* Desktop Framework: Tauri 2
* Frontend: React
* Language: TypeScript
* Native Layer: 필요 최소한의 Rust
* Agent Runtime: 로컬 Codex CLI / Codex app-server
* Codex Communication: 공식 app-server protocol
* User Files: Local Filesystem
* Remote Application Server: 없음
* Application Backend Server: 없음
* Cloud Database: 없음
* File Editing UI: 없음

다만 실제 최신 Codex 공식 인터페이스를 확인했을 때 더 단순하고 안정적인 공식 방법이 있다면 그 방법을 우선해도 된다.

비공식 API나 내부 endpoint를 역공학해서 사용하지 않는다.

# 5. PoC UI

디자인은 중요하지 않다.

첫 버전은 다음 정도면 충분하다.

```text
┌──────────────┬──────────────────────────┐
│ Files        │ Codex                    │
│              │                          │
│ test.md      │ > 사용자 입력           │
│ data/        │                          │
│              │ Codex 작업 상태         │
│              │                          │
│              │ 질문 / Approval         │
│              │                          │
├──────────────┴──────────────────────────┤
│ 5h Usage: --        Weekly Usage: --    │
└─────────────────────────────────────────┘
```

필요한 기능:

1. 로컬 폴더 선택
2. 현재 폴더의 간단한 File Tree
3. 사용자 입력창
4. Codex 응답
5. Codex 작업 상태
6. Approval 요청 UI
7. 사용자 질문 UI
8. 5시간 / 주간 사용량 표시
9. 마지막 채팅 이어하기
10. 새 채팅 시작

그 외 기능은 구현하지 않는다.

# 6. Codex Integration

Codex 관련 코드를 UI 코드와 강하게 결합하지 말고 얇은 Adapter / Bridge 계층을 둔다.

개념적으로 다음과 같은 역할이면 충분하다.

```ts
startCodex()

getAccount()

startChat(workspacePath)

resumeChat(chatId)

sendMessage(chatId, message)

respondToApproval(...)

respondToUserQuestion(...)

getRateLimits()
```

위 함수명은 제품 내부에서 이해하기 쉽게 표현한 예시일 뿐이다.

실제 Codex 공식 API 이름과 구조를 억지로 이 형태에 맞추지는 않는다.

예를 들어 공식 프로토콜이 내부적으로 `thread/start`를 사용한다면 Codex Bridge 내부에서는 공식 API를 그대로 사용한다.

목적은 다음과 같다.

```text
React UI
↓
Codex Bridge
↓
공식 Codex Protocol
```

Codex protocol이 변경될 경우 UI 전체를 수정하지 않고 Bridge 계층 중심으로 대응할 수 있어야 한다.

# 7. State 저장

MVP에서는 최소 상태만 저장한다.

예:

```text
lastWorkspace
lastChatId
```

필요하다면 최소한의 앱 설정만 추가한다.

다음 데이터는 별도로 복제해서 저장하지 않는다.

* 전체 채팅 내용
* 사용자 파일 사본
* 파일 Index
* AI Reasoning State
* 사용량 기록 DB

Codex가 관리하는 데이터는 가능한 한 Codex에게 맡긴다.

# 8. Error 처리

비개발자를 대상으로 하므로 Raw Error만 단독으로 노출하지 않는다.

그러나 **Raw Error를 숨기지도 않는다.**

사용자가 이해할 수 있는 설명을 먼저 보여주고, 그 아래에 실제 오류 정보를 함께 제공한다.

예:

```text
Codex 연결이 끊겼습니다.

Codex 프로세스와의 연결이 종료되었습니다.
다시 연결해서 작업을 계속할 수 있습니다.

[다시 연결]

자세한 오류:
process exited with code 1
```

인증 문제:

```text
ChatGPT 로그인이 필요합니다.

Codex를 사용하려면 다시 로그인해주세요.

[로그인]

자세한 오류:
<raw authentication error>
```

폴더 권한 문제:

```text
이 폴더의 파일을 수정할 수 없습니다.

현재 프로그램에 이 폴더의 쓰기 권한이 없습니다.

자세한 오류:
Permission denied: ...
```

원칙은 다음과 같다.

```text
사용자가 이해할 수 있는 설명
+
해결 가능한 경우 행동 버튼
+
Raw Error
```

Raw Error는 개발자뿐 아니라 문제를 검색하거나 지원을 요청하려는 사용자에게도 유용할 수 있으므로 확인 가능해야 한다.

가능하다면 Raw Error 영역은 접고 펼칠 수 있도록 한다.

예:

```text
오류 상세 보기 ▼
```

내부 개발 로그에는 더 자세한 원본 오류와 필요한 Diagnostic 정보를 남겨 디버깅할 수 있도록 한다.

# 9. 다양한 문서 파일 처리

이 제품의 주요 사용자는 개발자가 아니라 문서 작업을 많이 하는 일반 사용자다.

따라서 다음 형식은 중요한 검증 대상이다.

* PDF
* DOCX
* XLSX
* PPTX

또한 다음 기본 형식도 포함한다.

* TXT
* Markdown
* JSON
* CSV

다만 우리 프로그램 자체에 특정 문서 처리 라이브러리를 미리 강제로 내장하는 것을 기본 전략으로 삼지는 않는다.

우선 Codex에게 해당 파일을 처리하도록 요청하고 **Codex가 자신의 환경과 작업에 필요한 도구를 판단하도록 한다.**

예를 들어 Codex가 DOCX를 수정하기 위해 Python 라이브러리가 필요하다고 판단한다면:

```text
python-docx
```

XLSX 작업에 필요하다면:

```text
openpyxl
```

PDF 처리에 도구가 필요하다면 적절한 Python package 또는 로컬 CLI 도구를 선택할 수 있다.

PPTX 처리에도 마찬가지다.

즉:

```text
우리 앱이 문서 도구를 결정
❌

Codex가 작업을 분석
↓
필요한 도구 판단
↓
필요하면 설치 요청
↓
사용자 승인
↓
로컬 환경에 설치
↓
작업 수행
✅
```

를 기본 방향으로 한다.

# 10. Dependency 설치에 대한 원칙

Codex는 작업 수행을 위해 필요한 라이브러리나 도구를 자체적으로 판단할 수 있다.

예:

```text
pip install python-docx
npm install ...
brew install ...
winget install ...
```

등이 필요할 수 있다.

하지만 사용자의 컴퓨터 환경을 변경하는 작업이므로 **무조건 자동 설치하지 않는다.**

Codex가 설치를 필요로 할 경우 기존 Approval 시스템을 활용한다.

예:

```text
이 Word 문서를 수정하려면
'python-docx' 라이브러리가 필요합니다.

사용자의 컴퓨터에 설치하려고 합니다.

python -m pip install python-docx

[거부]    [설치 허용]
```

가능하면 다음 정보를 함께 보여준다.

```text
설치 대상
python-docx

설치 목적
DOCX 파일 읽기 및 수정

실행 명령
python -m pip install python-docx
```

Codex가 이미 설치된 다른 도구를 활용할 수 있다면 불필요한 설치는 하지 않는다.

우리 앱 자체가 별도의 Plugin Manager나 Package Manager를 만들지는 않는다.

Codex의 기존 command execution과 approval 흐름을 활용한다.

# 11. 문서 처리 PoC

기본 파일 작업을 확인한 뒤 실제 사용자 환경에서 다음 테스트를 수행한다.

### PDF

검증:

* 내용 읽기
* 여러 PDF 비교
* PDF 내용을 참고해 새 문서 생성

### DOCX

검증:

* 내용 읽기
* 새 DOCX 생성
* 기존 DOCX 수정
* 기본 서식 보존 여부

### XLSX

검증:

* 데이터 읽기
* 셀 수정
* 새로운 데이터 추가
* 수식/서식 보존 여부

### PPTX

검증:

* 슬라이드 내용 읽기
* 새 슬라이드 생성
* 기존 프레젠테이션 수정
* 레이아웃/서식 보존 여부

Codex가 작업 수행을 위해 필요한 라이브러리를 판단하고 설치하는 과정도 함께 검증한다.

중요한 것은 단순히 "파일을 열 수 있다"가 아니라:

> 일반 사용자가 실제로 사용하는 파일을 Codex가 얼마나 안전하게 수정할 수 있는가?

를 확인하는 것이다.

# 12. 구현 진행 방식

바로 모든 코드를 작성하지 말고 다음 순서로 진행해줘.

## Step 1 — Repository 분석

현재 프로젝트 구조와 파일을 확인한다.

기존 코드가 있다면 최대한 재사용한다.

불필요한 구조 변경은 하지 않는다.

---

## Step 2 — 로컬 Codex 환경 확인

현재 컴퓨터의 Codex 환경을 확인한다.

다음과 같은 내용을 확인한다.

* Codex 설치 여부
* Codex 버전
* app-server 실행 가능 여부
* 인증 상태
* 현재 플랫폼
* 필요한 로컬 실행 방식

이 프로그램이 **현재 컴퓨터의 Codex에 덧붙어 실행되는 로컬 프로그램**이라는 점을 항상 전제로 한다.

---

## Step 3 — 공식 Codex 인터페이스 확인

현재 사용할 Codex 버전을 기준으로 다음 기능의 실제 지원 방식을 확인한다.

* app-server 실행
* account / auth
* 채팅 시작
* 기존 채팅 이어하기
* 사용자 메시지 전달
* Streaming Event
* User Input Request
* Approval Request
* Rate Limits

추측해서 API를 만들지 않는다.

공식 API의 실제 이름이 `thread` 등의 용어를 사용하더라도 내부 구현에서는 그대로 사용할 수 있다.

단, 사용자에게 표시하는 UI에서는 `채팅` 또는 `작업`으로 표현한다.

---

## Step 4 — 구현 계획

실제 코드를 수정하기 전에 다음 내용을 짧게 정리한다.

* 사용할 구조
* 새로 생성할 주요 파일
* 수정할 기존 파일
* 필요한 Dependency
* 기술적으로 불확실한 부분
* 이번 PoC에서 명시적으로 제외할 부분

과도한 설계 문서는 만들지 않는다.

---

## Step 5 — 가장 작은 Vertical Slice 구현

가장 먼저 아래 시나리오 하나를 끝까지 동작시킨다.

```text
로컬 테스트 폴더 선택

↓

사용자:
"이 폴더에 test.md를 만들고
오늘 할 일을 3개 적어줘."

↓

Codex 작업 시작

↓

필요한 Approval 처리

↓

test.md 생성

↓

완료 메시지 표시
```

이 기능이 동작하기 전에는 부가 기능 개발로 넘어가지 않는다.

## Step 6 — 기본 P0 추가

# 13. 구현 중 판단 기준

어떤 기능을 추가하거나 구조를 복잡하게 만들기 전에 다음 질문을 한다.

> 이 기능이 없으면 현재 PoC가 동작하지 않는가?

YES → 구현 검토

NO → 구현하지 않음

> 이 기능은 Codex를 쉽게 사용할 수 있게 보여주는 것인가,
> 아니면 우리가 또 다른 프로그램을 새로 만들고 있는가?

후자라면 기본적으로 구현하지 않는다.

# 14. 제품의 경계

이 앱은 다음과 같은 프로그램이 되어서는 안 된다.

```text
❌ 웹 기반 AI Workspace
❌ 클라우드 문서 플랫폼
❌ 새로운 IDE
❌ Word 대체 프로그램
❌ 새로운 AI Agent Framework
❌ 자체 AI Backend
```

이 프로그램은 다음과 같은 프로그램이어야 한다.

```text
사용자의 컴퓨터
        │
        ▼
┌──────────────────┐
│    우리의 GUI    │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│     Codex CLI    │
│   / app-server   │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│   사용자의 파일   │
└──────────────────┘
```

즉 **Codex CLI의 로컬 능력을 일반 사용자에게 제공하는 얇은 GUI Layer**다.
